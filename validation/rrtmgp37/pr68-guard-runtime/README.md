# PR68 guard build and successful restart comparison

**Result: scoped exact parity for one daylight restart interval.** The PR65 executable and a copied executable built from the PR68 output-finite guard source both restarted from the same 2016-10-07 12:00 UTC checkpoint and completed through 13:00. With MPI4, OMP2, B32 and experimental frozen-optics mode 1, both processes returned 0, all four unique ranks reported success, and the 12:00 and 13:00 histories plus the 13:00 restart file were byte-identical across variables. Variable names, dimension maps, dtypes, shapes, and variable attributes matched. Raw and decoded output checks found no nonfinite, masked, or fill values.

The candidate PR68 binary is SHA256 `2b774cedb1b424252f0b5cd4f0d11635018c348911532b3451558a06e4299fe6` (59,183,616 bytes). It was compiled from source commit `89b66c0d85cc3a0a68c894157264e686dcfe99e9`; the two guard source files are included with their exact hashes. The original build runner receipt is retained as `BUILD_FAIL`: its strict footer predicate expected a period after the success phrase, while the actual compiler log emitted the decorated success line. The compiler process returned 0. The additive independent postflight reconciled that run, verified the footer, rebuilt radiation objects, all pinned build inputs/dependencies, and the executable. PR65 and PR68 used identical `configure.wrf` bytes and matching runtime library closures (50 resolved libraries each). This is a copied/incremental build, not a pristine full-source build.

The runtime comparison covers one hour, from elapsed hour 36 to hour 37 of the existing parent case. A separate comparison against the selected continuous-parent hour-37 record found no raw-array differences and matching variable sets. The `START_DATE` global attribute differs because the arms were restarted at 12:00. That parent comparison is diagnostic context. It does not extend the exact PR65-versus-PR68 comparison into a claim about restart/continuous metadata identity.

The run used the experimental frozen-optics mode 1 and a hash-pinned table. It does not validate optical accuracy, observational skill, long-forecast readiness, or the later PR70 radius-input-context diagnostic patch: the PR68 runtime binary predates that patch. No physics settings were changed between the two restart arms beyond each executable; both used identical staged namelists/assets and the same restart checkpoint.

The frozen plan contains one stale count: it says the PR68 arm has 104 staged entries, while the manifest, stage readback, and actual preflight show 105 for each arm. The runner validates every manifest entry and actual staged bytes. The count discrepancy is preserved here as a nonblocking plan-metadata note rather than silently corrected.

## Evidence and verification

`evidence/` contains the pinned plan, stage manifest/readback, root authorization, runtime receipt, independent runner and output-postflight reviews, build receipts, runtime closure, and the original failed build receipt. `source/` holds the exact guard source files. The configure and namelist snapshots in `config/` are unwrapped base64 encodings so their exact original whitespace is preserved without introducing trailing-space diff noise; the verifier checks each decoded byte hash and size. `logs/` contains small excerpts (the build-footer display excerpt has trailing whitespace trimmed); `manifest.json` records hashes and sizes for the full external logs, binaries, table, checkpoint, and parent history without copying large binaries or NetCDF files.

Run `python3 verify_artifacts.py` from this directory to validate all included artifact hashes and the core receipt chain. Add `--external` to check external file pins on a machine where the original build/run paths remain available. The package does not include executable binaries, coefficient tables, or full history/restart outputs.
